# 性能与契约验证

## 最新代码与旧版代码（2026-10-11）

本次重新运行两份实际代码：旧版是此前保留的 `mem::take` 快照，新版是当前
`clone` 实现，包含直接追加终止块的改动。没有沿用上次的计时数据。

| 位置 | 旧版 | 新版 |
| --- | --- | --- |
| 首个无分隔符的块 | `mem::take(&mut self.buffer)` 转移输入分配 | `self.buffer.clone()` 复制有效字节，随后消费输入 |
| 跨块段的终止块 | 先 `split_to(pos + 1)`，再复制到累积结果 | 直接复制 `available[..pos + 1]`，再 `consume(pos + 1)` |
| 后续无分隔符的块 | 追加 `&self.buffer` 后推进缓冲 | 追加 `available` 后统一调用 `consume` |

`BytesMut::clone` 在 bytes 1.10.1 中调用 `BytesMut::from(&self[..])`，会复制字节。
这是已核对的[源码行为](https://github.com/tokio-rs/bytes/blob/v1.10.1/src/bytes_mut.rs#L1345-L1349)。
本次同时包含首块保存方式和终止块处理方式的变化，不能将全部耗时差异归因于其中一项。

最终测量前，修正了新终止块路径的消费边界：`consume(pos)` 会留下分隔符，
应为 `consume(pos + 1)`。新增的
`bytes_reader_consumes_only_the_ending_of_a_spanning_line` 测试确认：CRLF 跨缓冲时，
消费完整行终止符，并保留下一个完整行。该测试在修复前失败、修复后通过。
测量期间的中间版本数据没有混入下面的最终样本。

### 条件

两版使用相同的 [spanning.rs](benches/spanning.rs)、Cargo.lock、bytes 1.10.1、
memchr 2.7.4、rustc/cargo 1.98.1，以及工作区 release 配置：LTO、单 codegen unit、
去除调试信息。机器仍为 Intel Core i7-13700KF / Microsoft 虚拟化 Linux。
先编译，再将进程固定到逻辑 CPU 0，六轮交替运行两版；每组预热一次、计时五次，
每版每组共 30 个样本，共 720 个最终计时样本。没有固定 CPU 频率或独占机器。

每次读取约 32 MiB 内存输入，缓冲大小为 8 KiB，行长包含 CRLF。计时包含读取器
构造、读取、结果保存和析构，排除输入生成。计时前完整验证载荷，每次检查总长度
和行数；立即处理模式只观察每行长度及首尾字节。没有磁盘 I/O 或业务解析。

## 历史：首块转移与首块复制（2026-10-11）

本节保留切换到 `clone` 前的测量，其中“当前”指当时的 `mem::take` 版本。

实测首块转移并不总是更快。短读并立即丢弃结果时，当前 `mem::take` 方案用时
减少约 19%；同样的输入保留全部结果时，用时约为复制方案的 5 倍，峰值 RSS
也明显增加。这次只增加基准与记录，没有修改生产读取实现。

比较的是两个独立 crate 快照中的完整 `read_line(Exclude)` 路径：

- `take`：当前 `Option<BytesMut>` 实现，首个无分隔符的块使用 `mem::take` 转移。
- `copy_first`：只将该首块分支替换为下面的复制操作，并移除未使用的 `mem` 导入。
  后续块的 `extend_from_slice` / `advance`、填充、查找和交付逻辑均相同。

```rust
out = Some(BytesMut::from(self.buffer.as_ref()));
self.buffer.advance(self.buffer.len());
```

完整差异保存在[对照补丁](benchmarks/2026-10-11-spanning-copy-first.patch)，仅用于
临时副本。这不是 `Option` 与其他状态表示的对比，也没有单独测量条件分支的指令成本。

### 方法与输入

基准为 [spanning.rs](benches/spanning.rs)。内存输入由非 UTF-8 字节 `0xff` 与 CRLF
组成，每组约 32 MiB，缓冲大小固定为 8 KiB。下表的行长包含 CRLF。

| 数据集 | 行长 | 底层单次读取上限 | 覆盖路径 |
| --- | ---: | ---: | --- |
| buffered_control | 64 B | 8 KiB | 完整行在缓冲内，不进入被比较的分支 |
| unaligned | 8,202 B | 8 KiB | 行起点逐渐错开，首块长度随位置变化 |
| two_blocks | 16 KiB | 8 KiB | 每行两块，转移或复制首块，再追加终止块 |
| four_blocks | 32 KiB | 8 KiB | 每行四块，还经过两次中间块追加 |
| long | 1 MiB | 8 KiB | 每行 128 块，多次追加和扩容 |
| short_reads | 2 KiB | 512 B | 每行四次短读，填充目标仍为 8 KiB |

立即处理只观察结果的长度、首尾字节，然后丢弃；持有模式保存全部 `BytesMut` 到
本轮结束。计时包含构造、填充、搜索、复制或转移、扩容、结果容器维护和析构，
不包含输入生成。每组先在计时外校验全部载荷字节，再执行一次不校验载荷的预热，
然后测量五次；每次都核对结果总长度和行数。没有磁盘 I/O 或业务解析。

使用 rustc 1.98.1 / cargo 1.98.1，依赖为 bytes 1.10.1、memchr 2.7.4。两份快照
从同一工作区复制 Cargo.lock，并显式采用相同的 release 配置：`lto = true`、
`codegen-units = 1`、`strip = "debuginfo"`。没有额外 RUSTFLAGS。
机器为 Intel Core i7-13700KF / x86_64 Linux / Microsoft 虚拟化环境，进程固定在
逻辑 CPU 0；未固定 CPU 频率，也未独占机器。编译完成后串行运行六轮，每轮交替
先运行哪个版本。每个版本、场景、保留方式共 30 个计时样本，总共 720 个。

### 峰值内存与解释

另外对两组持有场景分别运行独立进程，使用 GNU time 的 `%M` 获取峰值 RSS。
每个版本、场景测量三次；下面为中位数，单位 MiB。RSS 包括约 32 MiB 输入、
结果容器、读取器和运行时，且覆盖校验、预热和五次计时的整个进程，不是纯结果容量，
也不是内存泄漏测量。

| 数据集，持有至结束 | 首块复制 | 当前首块转移 |
| --- | ---: | ---: |
| unaligned | 72.32 | 95.19 |
| short_reads | 66.91 | 163.64 |

[峰值 RSS 原始 CSV](benchmarks/2026-10-11-spanning-rss.csv) 保存全部 12 次测量。

已确认的实现行为：`mem::take` 转移首块时不复制载荷，但也转移了它的分配；
下一次填充需要给空的输入缓冲分配空间。后续 `extend_from_slice` 仍会复制，并可能
为结果扩容；`advance` 本身只推进视图。bytes 1.10.1 的
[resize / reserve 实现](https://github.com/tokio-rs/bytes/blob/v1.10.1/src/bytes_mut.rs#L479-L740)
决定后续填充能否复用空间，
[extend_from_slice 实现](https://github.com/tokio-rs/bytes/blob/v1.10.1/src/bytes_mut.rs#L863-L879)
先预留容量再复制载荷。

在本次短读场景中，首块实际只有 512 B，转移方案却将 8 KiB 容量一起交给结果；
后续拼接成 2 KiB 行后仍保留该容量。复制方案从 512 B 开始累积，结果长到 2 KiB。
持有 16,384 个这样的结果时，容量差异会累积。这与测得的 RSS 差异一致；立即丢弃时
则没有这么多同时存活的结果，转移方案也省去了首块复制和小容量起步的增长过程。

工程判断：短读且长期持有结果时，本次证据支持首块复制方案；立即处理的同组负载
则支持转移方案。尚未统计分配次数、实际搬移字节数、缓存未命中或页面错误，不能
断言某个机制单独造成了全部耗时差异，也不能从这些合成数据推导普遍的最快方案。
